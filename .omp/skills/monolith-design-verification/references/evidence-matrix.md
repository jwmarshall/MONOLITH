# Runtime evidence matrix and representative scenarios

Read before browser work. This is a reusable procedure, not an execution log and not authorization for effects. Report actual coverage in chat. Inspect the synthetic runtime and harness before interactions; if a control could persist state, touch credentials, enqueue work or call a provider, do not activate it merely because it appears on a local page. Safe fixture controls must be explicitly permitted and isolated. Source inspection can examine dangerous controls without activating them. Classify presentation versus codebase-only identity acceptance first. Module/OTP/config/path/command-only changes with no rendered effect need no browser environment or visual gate; report source-only identity evidence and mark these runtime rows not applicable, never visually certified. The full identity target requires no compatibility aliases or rebrand-specific preservation/data migration; it never authorizes private-state operations.

## Evidence record

For each relevant row record: rule IDs; target/source `file:line`; actual route; state and synthetic owner/account identity; browser/version; CSS viewport dimensions; genuine zoom setting if available; output/preferences/emulation; fixture/harness and permitted interaction; steps; expected behavior; observed result; measurement method; artifact path; and coverage status. Do not expose private identity or credentials in captures/logs.

Use `OBSERVED PASS`, `OBSERVED FAIL`, `SOURCE-ONLY`, `UNRUN`, `UNAVAILABLE`, or `NOT APPLICABLE — <specific reason>`. Source-only is not a runtime pass. Unavailable rows identify the exact missing capability/fixture/safety permission, not a vague browser limitation. Use only applicable rows: an untouched mail reader is not an obligation in a sidebar-only migration, but every affected sidebar state is. Test regression paths affected indirectly by shared-owner changes. A row may have both source support and a separate observed browser result; never conflate them. For code-only scope, source-only evidence may satisfy expressly source-only acceptance; distinguish that result from a rendered UI pass.

## Representative skill-behavior scenarios

These cases define expected behavior of the workflow; they are not claims of execution and do not authorize a trial.

1. **Normal.** Caller names Home routes/states and changed register source, supplies an inspected loopback fake-provider server, clean synthetic profile, permitted ephemeral fixture toggles and disposable artifact destination. Build the applicable matrix, invoke exact native source reviewers if available, observe relevant viewport/keyboard/zoom/motion/colors/print/contrast/state rows, and report `[PASS]` only with all verdict-essential evidence and no mandatory violation. Genuine failures return `[FAIL]` with reproduction, not repairs.
2. **Missing.** Caller says “verify the redesign” with no selected targets/routes/states/acceptance. Inspect available context, then return `[INSUFFICIENT DATA: Missing verification scope]` listing only unresolved inputs. Do not silently test the study instead or choose broad scope.
3. **Forbidden.** A local connection page uses real storage, and its reconnect/generation controls might access credentials, enqueue provider work or incur cost. Do not click, read private files or copy a user browser profile. Return `[BLOCKED: Unsafe verification environment]` or `[BLOCKED: Authorization required]` for the relevant missing boundary; source-only review remains possible. A separate authorization does not turn this skill into a repair or private-data workflow.
4. **Conflict.** Caller requests a passing verdict for unknown counts displayed as zero, or both approved normal-flow sidebar and contradictory overlay drawer. Return `[BLOCKED: Conflicting requirements]` with exact conflicting rules/caller requirement; never fake pass or silently compromise. Old visual styling alone is not a conflict when the selected MONOLITH replacement is authorized.
5. **No runtime.** Browser/server is absent or cannot be safely isolated. Return `[BLOCKED: Runtime unavailable]` and explicit `SOURCE-ONLY` findings/UNAVAILABLE rows. Do not install tools, run production or treat screenshots/source tokens as current runtime proof.
6. **Unavailable zoom or print output.** Browser can resize/emulate media but cannot expose genuine zoom/final print preview. Report available observations separately, mark necessary unavailable rows and return `[INCOMPLETE: Acceptance evidence missing]` absent confirmed failure. Do not label CSS zoom or print-media emulation equivalent.
7. **Native reviewer missing.** Exact-name invocation is unavailable. Label available portable/bundled-rule review `PORTABLE FALLBACK — not native invocation`, preserving read-only scope and limits; if essential review cannot be completed, return `[BLOCKED: Reviewer unavailable]`. Never invent native delegation output.
8. **Confirmed defect plus missing evidence.** At 320px an actual selected action clips, and forced-colors capability is unavailable. Return `[FAIL]` with M12 reproduction and unavailable forced-colors row; the missing row does not erase the defect or authorize a source repair.

## Report shape

- Outcome and precise selected scope; `SOURCE-ONLY` where applicable.
- Environment/isolation, actual browser/fixture/artifact destination and interaction authority.
- Rule-linked source findings with file/line, scenario, impact, expected/observed behavior; specialist identities and actual verdicts, with fallback label if applicable.
- Compact matrix: route/state/rule, actual viewport/zoom/mode, steps and observation, coverage status, genuine artifact/measurement reference.
- Checks actually run and results; failed, unrun or unavailable checks and exact prerequisites.
- Verdict-essential gaps versus advisory polish; no whole-app claim from a scoped exercise, no permanent status file and no repairs.
